# LoadPilot — LLM დისპეჩერის ასისტენტი SuperDispatch-ის ლოადებისთვის

LoadPilot არის ლოკალურად გაშვებულ დიდ ენის მოდელზე (Qwen2.5) დაფუძნებული აგენტი, რომელიც ეხმარება დამოუკიდებელ ავტოგადამზიდს/დისპეჩერს SuperDispatch-ის ტიპის ლოადების დაფაზე გადაწყვეტილების მიღებაში: პოულობს ლოადებს, ითვლის წმინდა მოგებას deadhead-ისა და საწვავის გათვალისწინებით, ადარებს ლეინებს, ინახავს ლოადებს watchlist-ში და ბუნებრივ ენაზე ხსნის, რომელი ლოადი ღირს აღებად.

> **მოდელი:** `Qwen/Qwen2.5-3B-Instruct` (Apache-2.0, ლოკალურად, `transformers`-ით).
> **ენა:** ინტერფეისი და პასუხები ქართული ან ინგლისურია — მოდელი პასუხობს მომხმარებლის ენაზე.
> **მონაცემები:** ნაგულისხმევად 24 ლოადის დემო დაფა; რეალური API/ექსპორტის ჩართვა შესაძლებელია გარემოს ცვლადებით (იხ. ქვემოთ).

## 1. რა პრობლემას ჭრის და ვისთვის

ავტოტრანსპორტის ლოადის არჩევისას მთავარი შეცდომაა მხოლოდ „დიდი rate“-ის ყურება. რეალური მოგება დამოკიდებულია:

- **deadhead-ზე** — რამდენი ცარიელი მილის გავლა გიწევს pickup-ამდე;
- **საწვავის ხარჯზე** — MPG და დიზელის ფასი;
- **ფიქსირებულ ხარჯზე** — მილის ღირებულება (მომსახურება, დაზღვევა, საბურავები);
- **loaded vs total miles** — rate per loaded mile შეიძლება კარგი ჩანდეს, მაგრამ total miles-ზე მოგება გაქრეს.

LoadPilot ამას აკეთებს სწრაფად, გამჭვირვალე ფორმულით და ყოველ რიცხვს ხელსაწყოთი ითვლის — მოდელი არ „იგონებს“ არითმეტიკას.

**მომხმარებელი:** დამოუკიდებელი ავტოგადამზიდის მძღოლი ან მცირე დისპეჩერი, რომელიც დღეში ათეულობით ლოადს ათვალიერებს და გადაწყვეტილებას 5–10 წუთში იღებს.

**რას აკეთებს აგენტი:**

- ეძებს ლოადებს სახელმწიფოების, pickup თარიღის, trailer-ის ტიპისა და rate-ის მიხედვით;
- ალაგებს ლოადებს რეალური წმინდა მოგებით (deadhead-ის ჩათვლით);
- ითვლის ერთი ლოადის P&L-ს, break-even rate-სა და effective RPM-ს;
- აფასებს ლეინის საშუალო rate-ს;
- ინახავს ლოადებს watchlist-ში შენიშვნებით;
- ხსნის, რატომ არის ლოადი კარგი/ცუდი და რა აკლია გადაწყვეტილებისთვის.

**რას არ აკეთებს:** არ ჯავშნის ლოადს, არ აწარმოებს მოლაპარაკებას, არ ამოწმებს ბროკერის კრედიტს, არ იცის ამინდი/საგზაო მოძრაობა/HOS.

## 4. აგენტის ტიპი: utility-based (ვიტილიტარული)

LoadPilot **utility-based** აგენტია. მიზანი მარტივია („იპოვე მისაღები ლოადი“), მაგრამ ერთი მიზნის მიღწევის მრავალი გზა არსებობს და მათ შორის არჩევა უტილიტის ფუნქციით ხდება: წმინდა მოგება, effective RPM, deadhead-ის წილი და break-even rate.

- **simple reflex** არ გამოდგება, რადგან გარემო ნაწილობრივ დაკვირვებადი და დინამიურია — წინასწარ ჩაწერილი „თუ rate > X, აიღე“ წესი deadhead-სა და ხარჯებს ვერ ჩათვლის.
- **model-based reflex** მხოლოდ მდგომარეობის შენარჩუნებას იძლევა, მაგრამ არ ადარებს ალტერნატივებს.
- **goal-based** ამოწმებს, მიაღწია თუ არა მიზანს, თუმცა ორი „მისაღები“ ლოადიდან უკეთესს ვერ აირჩევს.
- **utility-based** პირდაპირ ადარებს კანდიდატებს `net_profit`/`effective_rpm`-ით და ირჩევს მაქსიმალურ სარგებელს; ეს აუცილებელია სტოქასტურ და თანმიმდევრულ გარემოში, სადაც ერთი არჩევანი მეორეს გამორიცხავს.

აგენტს აქვს **model-based** კომპონენტიც — ხარჯების მოდელი და დაფის მდგომარეობა — მაგრამ გადაწყვეტილების ბირთვი უტილიტის მაქსიმიზაციაა.

## 5. არქიტექტურა

```text
მომხმარებელი (CLI / Colab)
        │  ბუნებრივი ენა
        ▼
   Agent loop  ──────────────►  LocalLLM (Qwen2.5, transformers)
        │  ერთი JSON ქმედება              │
        │  {"tool": ..., "args": ...}     │
        ▼                                 │
   Tool registry (schema validation)      │
        │                                 │
        ├── search_loads                  │
        ├── rank_loads                    │
        ├── calculate_profit              │
        ├── route_distance                │
        ├── watchlist                     │
        └── market_stats                  │
        │                                 │
        ▼                                 │
   data_source: API → ფაილი → დემო        │
   watchlist.json, cities.json            │
        │                                 │
        └── TOOL_RESULT ──────────────────┘
                    │
                    ▼
             {"answer": "..."}
```

**ციკლი:**

1. მოდელი იღებს system prompt-ს (როლი, წესები, tool-ების სქემები, JSON ფორმატი) და მომხმარებლის შეტყობინებას.
2. მოდელი აბრუნებს **ზუსტად ერთ** JSON ობიექტს: tool-ის გამოძახება ან საბოლოო პასუხი.
3. Python ამოწმებს არგუმენტებს JSON Schema-სა და ტიპებზე, შემდეგ ასრულებს tool-ს.
4. tool-ის შედეგი (ან შეცდომა + hint) ბრუნდება მოდელთან `TOOL_RESULT`-ის სახით.
5. ციკლი მეორდება მაქსიმუმ 8 ნაბიჯამდე; ბიუჯეტის ამოწურვისას მოდელი იძულებით აბრუნებს საბოლოო პასუხს.

**მთავარი პრინციპი:** გადაწყვეტილებას იღებს მოდელი (რომელი tool, რომელი არგუმენტები, როდის დასრულდეს), ხოლო Python პასუხისმგებელია ვალიდაციაზე, არითმეტიკასა და უსაფრთხოებაზე. კოდში არ არის „if request contains TX then search“ ტიპის წესები.

## 7. ხელსაწყოები (6)

თითოეულ tool-ს კოდში აქვს docstring: სახელი, აღწერა, პარამეტრები და დაბრუნების ფორმატი.

| # | Tool | რას აკეთებს | ძირითადი პარამეტრები | აბრუნებს |
|---|---|---|---|---|
| 1 | `search_loads` | ლოადების ძებნა დაფაზე | `origin_state`, `dest_state`, `pickup_after`, `trailer_type`, `min_rate`, `max_rate`, `limit` | `{ok, source, count, loads[], hint?}` |
| 2 | `rank_loads` | ლოადების რანჟირება წმინდა მოგებით, deadhead-ის ავტომატური გაანგარიშებით | `driver_city`, `origin_state`, `dest_state`, `pickup_after`, `trailer_type`, `limit`, `sort_by`, `mpg`, `diesel_price`, `fixed_cost_per_mile` | `{ok, driver, matched_count, loads[]}` — თითოეულში `net_profit`, `effective_rpm`, `verdict` |
| 3 | `calculate_profit` | ერთი ლოადის ან ჰიპოთეტური ლოადის P&L | `load_id` ან `rate_usd`+`loaded_miles`; `deadhead_miles`, `mpg`, `diesel_price`, `fixed_cost_per_mile`, `target_effective_rpm` | `{ok, total_miles, fuel_cost, fixed_cost, net_profit, effective_rpm, break_even_rate, verdict}` |
| 4 | `route_distance` | ორ ქალაქს შორის მანძილის შეფასება offline ცხრილით | `origin`, `destination` | `{ok, miles, drive_hours, method, disclaimer}` |
| 5 | `watchlist` | ლოადების შენახვა/ნახვა/წაშლა | `action` (`add/list/remove/clear`), `load_id`, `note`, `confirm` | `{ok, action, count, entries[], entry?}` |
| 6 | `market_stats` | ლეინის საშუალო/მედიანა rate და RPM | `origin_state`, `dest_state`, `trailer_type`, `min_loads` | `{ok, count, avg_rate, median_rate, avg_gross_rpm, best_lanes[]}` |

### მოგების ფორმულა (`calculate_profit`)

```text
total_miles   = loaded_miles + deadhead_miles
fuel_cost     = total_miles / mpg × diesel_price
fixed_cost    = total_miles × fixed_cost_per_mile
net_profit    = rate_usd − fuel_cost − fixed_cost
effective_rpm = net_profit / total_miles
break_even    = fuel_cost + fixed_cost
```

ნაგულისხმევი მნიშვნელობები: `mpg=6.5`, `diesel_price=3.75`, `fixed_cost_per_mile=0.35`, `target_effective_rpm=0.45`. ყველა პარამეტრი მოდელს შეუძლია შეცვალოს მომხმარებლის მონაცემებით.

**ვერდიქტი:** `excellent` (≥1.35× target), `good` (≥target), `marginal` (≥0.7× target), `pass` (დაბალი).

### 10.2 რა ხდება, როცა მოდელი არასწორ tool-ს ირჩევს ან ვერ ირჩევს

- **არასწორი tool:** თუ მოდელი წერს ახლო სახელს (`watch_list`, `market-stats`, `calculate_profits`), registry `difflib`-ით ავტომატურად ასწორებს მას ნამდვილ tool-ზე და შედეგში აბრუნებს `resolved_tool`-ს. სრულიად უცხო სახელი (`weather`) მაინც ბრუნდება `{ok:false, error, hint}`-ით.
- **უცნობი არგუმენტი:** მაგ. `rank_loads(deadhead_miles=100)` — ის თვითონ ითვლის deadhead-ს `driver_city`-დან, ამიტომ აგენტი ერთხელ იმეორებს გამოძახებას ზედმეტი ველის გარეშე და პასუხში რჩება `repaired_args`-ის კვალი.
- **კონფლიქტური არგუმენტები:** `calculate_profit`-ში `load_id`-სა და `rate_usd`/`loaded_miles`-ის ერთდროულად მოცემისას `load_id` პრიორიტეტულია; ზედმეტი რიცხვები იგნორირდება და პასუხში `ignored_inputs` არის მითითებული.
- **ვერ ირჩევს (არასწორი JSON):** tolerant parser ამოიღებს JSON-ს code fence/პროზის გარემოცვიდან; წარუმატებლობისას მოდელი იღებს `FORMAT ERROR`-ს და 3 ცდამდე ასწორებს. მერე ბრუნდება საუკეთესო ტექსტური პასუხი (`stopped_reason="format_fallback"`).
- **იმავე tool-ის გამეორება:** წარმატებული გამოძახების ზუსტი გამეორება დაუყოვნებლივ იბლოკება (არა მესამედზე) და მოდელი იღებს შეტყობინებას, გამოიყენოს უკვე მიღებული შედეგი.
- **watchlist-ის ცვლილება:** `add`/`remove`/`clear` სრულდება მხოლოდ მაშინ, თუ მომხმარებელი ცხადად ითხოვს შენახვას/წაშლას (`watchlist`, `add to`, `save`, `შეინახე`, `დაამატე` და ა.შ.). წინააღმდეგ შემთხვევაში აგენტი აბრუნებს `{ok:false, error:"watchlist modification was not requested"}`-ს და პასუხობს კითხვაზე — ეს იცავს მომხმარებელს მოდელის „თვითნებური“ ჩანაწერებისგან.
- **დაუმთავრებელი ორნაბიჯიანი მოთხოვნა:** თუ მომხმარებელი ითხოვს „იპოვე საუკეთესო და შეინახე watchlist-ში“, ხოლო მოდელი მხოლოდ `rank_loads`-ს იძახებს, `_finalize` ავტომატურად ამატებს პირველ ლოადს watchlist-ში და პასუხში წერს `Saved SD-xxxx to your watchlist.` — ეს მხოლოდ ცხადი მოთხოვნის შესრულებაა და არა ახალი ინფორმაციის გამოგონება.
- **დაჯავშნის მოთხოვნა:** თუ მომხმარებელი ითხოვს ჯავშანს (`book`, `reserve`), ხოლო მოდელის პასუხი არ შეიცავს უარს, `_finalize` წინ უმატებს `I can't book loads or contact brokers.`-ს. აგენტი არასოდეს ამტკიცებს, რომ ჯავშანი შეასრულა.
- **deadhead-ის ვარაუდი:** თუ `rank_loads`-ის შედეგში `deadhead_warning` არის (მძღოლის ქალაქი არ იყო მოცემული), ხოლო მოდელმა ეს არ ახსენა, `_finalize` პასუხს ამატებს `Note: driver_city was not provided...`-ს. ასე მომხმარებელი ვერ მიიღებს ოპტიმისტურ რანჟირებას ვარაუდის დამალვით.
- **გამოგონილი `driver_city`:** თუ მოდელი `rank_loads`-ს გადასცემს ქალაქს, რომელიც მომხმარებლის შეტყობინებაში საერთოდ არ ჩანს (მაგ. „Rank the Texas to Georgia loads“ → `driver_city="Dallas, TX"`), აგენტი ქალაქს ხსნის და tool-ს უგზავნის `driver_city=None`-ით; შედეგად ბრუნდება ნამდვილი `deadhead_warning` და არა გამოგონილ ლოკაციაზე დაფუძნებული „ოპტიმალური“ რანჟირება.
- **load ID-ების გამოტოვება:** თუ tool-მა ლოადები დააბრუნა, მაგრამ საბოლოო პასუხში ვერცერთი ID არ ჩანს, `_finalize` პასუხს ამატებს `Load IDs: SD-1006`-ს. ეს არ ცვლის მოდელის ტექსტს, მხოლოდ ხილულს ხდის იმას, რაც tool-მა უკვე დააბრუნა.
- **ნაბიჯების ლიმიტი (ნაგულისხმევი 8; შეფასებაში 5):** მოდელი იძულებით აბრუნებს საბოლოო პასუხს ხელსაწყოების გარეშე.
- **მოდელის ჩავარდნა/OOM:** აგენტი აბრუნებს გასაგებ შეტყობინებას `stopped_reason="llm_error"`-ით და არ იშლება.

### 10.3 სად და როგორ ტყდება აგენტი (README-ის სავალდებულო აბზაცი)

LoadPilot ყველაზე ხშირად ტყდება სამ ადგილას: **(1) ბუნდოვანი მოთხოვნის ინტერპრეტაციაზე** — 3B მოდელი ზოგჯერ „კარგ ლოადზე“ ფილტრის გარეშე ეძებს ან ხელსაწყოს ნაცვლად პირდაპირ პასუხს იწყებს, ამიტომ system prompt ითხოვს დაზუსტებას და ტესტები სწორედ ამას ამოწმებს; **(2) JSON ფორმატზე** — პატარა მოდელი ხან code fence-ს, ხან დამატებით ტექსტს ამატებს, რასაც tolerant parser და 3-ჯერადი `FORMAT ERROR` შესწორება იჭერს, მაგრამ სამივე ცდის ჩავარდნისას აგენტი ნაწილობრივ პასუხს აბრუნებს; **(3) მონაცემებზე** — დემო დაფა სტატიკურია, API subscription-ს მოითხოვს და მისი ველების სქემა ანგარიშზეა დამოკიდებული, ხოლო `route_distance` მხოლოდ haversine შეფასებაა და არა სატვირთო მარშრუტი. გარდა ამისა, აგენტი ვერ ჯავშნის ლოადს, ვერ ამოწმებს ბროკერის კრედიტს და ვერ ითვალისწინებს ამინდს/HOS-ს — ეს განზრახ არის გარეთ დატოვებული, რადგან ასეთი მოქმედებები ადამიანის დადასტურებას მოითხოვს.

- **ხარჯების მოდელი გამარტივებულია** — საწვავი + ფიქსირებული $/mi; არ მოიცავს ტოლებს, რემონტს კონკრეტულ მარშრუტზე, დაზღვევის კლასს ან ცარიელი დაბრუნების ხარჯს.
- **3B მოდელი** შეიძლება შეცდეს tool-ის არჩევაში, JSON-ის ფორმატში ან გრძელ მრავალნაბიჯიან მსჯელობაში; 7B 4-bit უფრო სტაბილურია.
- **ბუნდოვანი მოთხოვნა** — 3B ზოგჯერ „მაჩვენე კარგი ლოადი“-ზე დაზუსტების ნაცვლად ნაგულისხმევ ლეინს ირჩევს (T12). system prompt და few-shot მაგალითი დაზუსტებას ითხოვს, მაგრამ მოდელი ყოველთვის არ მიჰყვება; ეს არის შეფასებაში დარჩენილი ერთადერთი FAIL და განზრახ დოკუმენტირებულია, როგორც მოდელის შეზღუდვა.
- **ქართული ენა** შეზღუდულია მოდელის შესაძლებლობებით; ტექნიკური ტერმინები ინგლისურად რჩება.
- **watchlist ლოკალური JSON-ია** — ერთი მომხმარებელი, არა კონკურენტული წვდომა ან ღრუბლოვანი სინქრონიზაცია.
- **ავტომატური მონიტორინგი არ არის ჩაშენებული** — აგენტი პასუხობს მოთხოვნაზე; პერიოდული polling ცალკე ვოტჩერის ამოცანაა.
- **კონტექსტის ლიმიტი** — ძალიან გრძელი ისტორია ან დიდი tool-ის შედეგი იჭრება; ამიტომ დიზაინში შედეგები კომპაქტურია.

## 15. რეპოზიტორია და commit-ები

პროექტი ინდივიდუალურია — ყველა tool და commit ერთ ავტორს ეკუთვნის. ჯგუფური ვერსიისთვის რეკომენდებული სტრუქტურა: თითო წევრი თავის tool-ს ცალკე commit-ით ამატებს (`feat: add watchlist tool`), ხოლო README-ში მითითებულია ავტორი.

```bash
git init
git add .
git commit -m "feat: LoadPilot local LLM dispatch agent"
git branch -M main
git remote add origin https://github.com/YOUR_USER/superdispatch-agent.git
git push -u origin main
```

> commit-ების ავტორი: `git config user.name "..."` და `git config user.email "..."` — გამოიყენე შენი GitHub-ის მონაცემები, რომ ისტორია შენს ანგარიშს დაუკავშირდეს.
